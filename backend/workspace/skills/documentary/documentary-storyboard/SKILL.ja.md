# ドキュメンタリープロジェクト：絵コンテ追加仕様（ナレーション骨格 → 実測音声 → 設計カード）

`storyboard-breaker` の基本仕様の上に重ねられる。矛盾する場合は**本ファイルを優先**する。

ドキュメンタリーの分解は、実際の音声合成を挟んだ**二つの連続した段階**からなる：

```
最終脚本本文
  → 【第1段階】ナレーション骨格：逐語分割してショットごとの narration_text + タイトルへ（save_storyboards）
  → 人間が骨格を確認
  → 一括 TTS：各ショットに**実測**の音声長が付く
  → 【第2段階】設計カード：実測時間に基づき情報点／レイヤー段／生成段／予算を設計（update_storyboard）
```

**第1段階は視覚設計を一切産出しない**：実測時間がなければ、どんな段の予算も推測にすぎない。
**第2段階はナレーション本文を変更しない**：境界は第1段階で確定し、すでに音声化されている。一文字の変更が音声を無効にする。

いま自分がどちらの段階かは、ツールと指示で分かる：`save_storyboards` を呼ぶ＝第1段階、
「設計カードを書け」と指示され `update_storyboard(storyboard_id, design_card)` のみ許される＝第2段階。

# 第1段階：ナレーション骨格

## 1.1 ナレーション欄 = 脚本本文の逐語コピー（ハードルール）

本プロジェクトの脚本本文は**そのままナレーション原稿**である。本文を順に区切り、各区間を**原文のまま** `narration_text` に書く：

- **逐語コピー**：句読点・年号・人名・地名・数字をすべて原文と一致させる。書き換え・推敲・省略・加筆は一切不可。
- **文単位で切る**：句点／疑問符／感嘆符／セミコロンの直後でのみ切る。文の途中で切ってはならない。
- **追加も欠落も不可**：本文の全段落がいずれかのショットに収まること。全ショットの `narration_text` を順に連結すると脚本本文に一致する。
  `save_storyboards` は毎回 `script_coverage.gaps` と `must_fix` を返す：**隙間が残る限りショットを足し続ける**。
  文の境界で新しい `shot_number` を挿入し、漏れた文を逐語で取り込む。隙間を残したまま終えるとタスク全体が失敗になる。
- 1ショット **80 文字以内**（音声合成の1セグメント硬性上限）。原文の段落が 80 文字を超える場合は文の境界で隣接2ショットに分ける。
- **1ショットは段落をまたがない**：脚本の空行で区切られた各自然段落は一つの**論理グループ**である（原作者は一段落で一つの意味を表す）。
  段落境界は必ずショット境界になる。段落をまたぐショットは**保存拒否**され、返答に段落境界の位置が示される。絵コンテ設計はグループ単位で画面を統一的に計画する。
- ツールが検証する：`narration_text` は脚本本文中に逐語で見つかり、かつ本文と同じ順序でなければならない。書き換えた文は**保存拒否**される。

## 1.2 サーバが強制する3つの拒否ルール

違反ショットは黙って修正されず、**保存拒否**され理由付きで `rejected[]` に並ぶ。`rejected[]` を見たら理由に従って直し、再保存する。

1. **本話のショット数の硬性上限**：まず `units` ＝各段落で「文境界で隣接文を 80 字まで詰める」のに必要な最少ショット数の合計を求め、
   `cap = max( min(ceil(段落数 × 1.5), 段落数 + 3), min(ceil(units × 1.5), 2 × units − 段落数 + 3) )`。
   「段落数」＝脚本本文を空行で分割した非空段落の数。`cap` を超えるショットは一律拒否。骨格分割のタスク説明に本話の最少ショット数と上限が明記される。
   **同じ段落の隣接文は 1 ショットにまとめる**。もう 1 文足すと 80 字を超えるところまで詰め、情報点が明確に切り替わるときだけ早めに切る。1 文 1 ショットにしない——上限を使い切って未割当の本文が残ると、タスク全体が失敗する。
2. **各ショットは必ずナレーションを担う**：`narration_text` が空なら拒否。ドキュメンタリーに無音の画面のみのショットは存在しない。
   空ショット、トランジション、地図の定場も一区間のナレーションを担う。
3. **同じナレーションを二つのショットが取ってはならない**：同一文（または重複区間）を取った時点で拒否。

## 1.3 この段階で書くのは4項目だけ

`save_storyboards` のドキュメンタリー用スキーマが受け取るのは：

- `shot_number`：ショット番号。
- `narration_text`：本ショットのナレーション（逐語、1.1 参照）。
- `title`：本ショットの主情報点を一文で（「イルティシュ川が唯一の水路である」「近衛連隊出身が指揮権を決めた」）。
- `continuity`：`continue` / `cut`。前ショットとの接続。判断がつかなければ送らない。

**設計カード・画面描写・キーフレームプロンプト・動画プロンプト・尺・アセット紐付けは一切書かない**。
それらは第2段階に属し、第2段階はこのショットが実際に音声化され実測秒数が得られてから始まる。
いま書ける秒数はすべて推定であり、**本ワークフローは推定を受け付けない**。

## 1.4 一ショット一情報点

ショットの境界は尺ではなく**情報点**が決める：一ショットで一つのことを言い切り、言い終わったら切る。
`title` の一文は第2段階で `design_card.info_points[0].text` になる。

情報点と画面が噛み合わないときは、第2段階で**画面を直す**。ナレーションに戻って直してはならない。

# 第2段階：実測ナレーション時間に基づく設計カード

## 2.1 前提（サーバが強制、迂回不可）

- 本話の**ナレーション骨格が人間によって確認済み**であること；
- 本ショットに**現在有効な音声がある**こと：本文・発音マークアップ・現在有効な音声パラメータが音声と一致し、
  音声ファイルが存在し、そこから有限の正の時間が実測されていること。

指示には本ショットの**実測音声秒数**が明示される。これはファイルから測った事実であり、文字数からの推定ではない：
**予算は必ずこれに従う**。「毎秒 4.5 文字」の推定口径はこの段階では使わない。

## 2.2 設計カード `design_card`（全ショット必須）

### 2.2.0 まず本グループの視覚計画を見る

設計カードは**論理グループ**（ナレーション原稿の一つの自然段落）単位で統一的に計画する：バッチがまずグループ全体に対して一度
グループレベルの視覚計画を立て（どのショットでどのベース画像を使うか、どの画像をどのショットで完全に確立するか、
その後どのショットが短い提示だけを行うか、どのショットを生成段に任せるか）、それからショットごとにカードを記入する。
指示には**本グループの計画と本ショットの項目**が示される：

- **本ショットの項目に従って組み合わせとベース画像を記入する**；本ショットに割り当てられた追加項目は画面に落とす
  （`must_mark` + `planned_layers`）。追加項目を割り当てられていないショットでは、すでに確立した地理情報をまた全画面で描き直さない。
- 計画項目の「ピクチャー・イン・ピクチャー」は `planned_layers` の `type:'image'` レイヤーとして書き、`anchor.asset_id` を
  **その画像自身の本集アセット id** に向ける（画面に入れる挿絵そのもの）。意味エントリでもベース画像でもない。
- 実現できない場合（素材に注記が無い、予算に収まらない）は黙ってやり方を変えない：2.2.7 に従って処理し、`rationale` に逸脱の理由を書く。
  カードが計画と一致しない場合は `group_plan_deviation`（警告）と判定され、人が確認する。
- レンダリング上の事実：完成映像はショット番号順のハードカットでつながる。レイヤー段は各ショットごとに**きれいな全画面のベース画像からやり直し**になり、
  前ショットで描いたレイヤーは引き継がれず、レイヤーは最短でも 0.2 秒で現れる。すでに現れたベース画像で始めるときは、
  `at_s=0.2` の引き継ぎレイヤーでそれまでに描いた状態を復元し、最初の追加項目の `at_s ≤ 1` にする。

画面を書く前に次の連鎖をたどり、結論を `design_card` に記す：

```
このショットで観客に届ける情報（info_points[]、12 件以内）
  → どれをレイヤー段が描くか（layer_plan：ベース画像 base ＋ 必須注記 must_mark[] ＋ 計画レイヤー planned_layers[]）
  → どれを生成段が演じるか（gen_plan：参照アセット reference_assets[] ＋ 先頭/中間/末尾フレームの描写）
  → 各段の秒数（budget：layer_s / gen_s）。合計は実測音声時間以上でなければならない
  → なぜそう配分したか（rationale、600 字以内）
```

### 2.2.1 `info_points[]`：伝える情報と、その担い手

各項目 `{ id, text, via }`、最大 12 件：

- `id`：ショット内で一意の短い識別子（`p1`、`p2`…）。`planned_layers` や `rationale` から参照できる。
- `text`：その情報を一文で（「ジュンガルの支配範囲はバルハシ湖まで及ぶ」）。
- `via ∈ layer | generated | narration_only`：
  - `layer` —— レイヤー段がベース画像上に示す（範囲・経路・地点・ネームバー・年代）。**初出**の地理情報は必ず画面に落とし、
    本グループの計画が本ショットに割り当てた追加項目と一致させる。
  - `generated` —— 生成段が演じる（出発・行軍・交戦・謁見のような過程のある出来事）。
  - `narration_only` —— ナレーションのみが担い画面は負担しない。前のショットですでに確立し、本ショットでは再言及するだけの地理背景は
    これを記入し、`rationale` にどのショットが担うかを明記する。一ショットに多すぎる場合は画面が働いていない。

すべての情報点に担い手が必要。担い手のない項目は `info_point_unassigned`（警告）になる。

### 2.2.2 `layer_plan`：レイヤー段の計画

- `base`：レイヤー段のベース画像。既存素材の具体的なバージョンを指す `{kind:'asset', asset_kind, asset_id, version_task_id}`、
  または前ショットの末尾フレーム画面を引き継ぐ `{kind:'inherit_prev'}`（単なる画像で意味注記が無く、その上にレイヤーをアンカーできない）。
  **用図は一貫、出図は節度**：同一の語りの段の地理的証拠は同じ一枚の画像に固定する（毎ショット地図を差し替えない）。ただし「素材を共有する」
  ことは「毎ショットその図に戻る」ことではない——いつそれを開くかは本グループの視覚計画が決める（2.2.0）。
- `must_mark[]`：本ショットでベース画像上に必ず示す意味項目。各項目 `{ asset_id, semantic_id, name }` を
  `read_storyboard_context` が返す `semantics` 一覧から**逐語コピー**する（`asset_id` ＋ `id` ＋ `name` の三点すべて一致）。
  名称を創作すると `unresolved` と判定され設計カード画面で赤くなる。書かなかったのと同じである。
  ナレーションに現れる地名・水系・湖・城塞・政権範囲・経路はここに対応項目が見つかるはずである。
  本話にその意味項目が無い場合、人手の注記待ちとして**空の `must_mark` を書いてはならない**。そのアセットの既存注記が実際に支える
  表現に変えるか、その項目を本当に持つアセットに差し替える。どちらも無理なら 2.2.7 に従って不足を説明し、このカードを保存しない。
- `planned_layers[]`：どのレイヤーをどの順で出すか。各項目
  `{ type, text?, anchor?: {asset_id, semantic_id, name}, role?, fields?, at_s }`：
  - `type ∈ polygon | polyline | marker | label | text | image`
    （範囲ハイライト／河川・経路・矢印／地点／意味位置に固定する地名／画面文字テンプレート枠／ピクチャー・イン・ピクチャーの小図）。
  - **ピクチャー・イン・ピクチャー**：`{ type:'image', anchor:{ asset_id } }` で、画像を持つ別のアセット（詳細地図・全体図・档案画・器物図）を
    本ショットのベース画像の隅に置く。再言及の短い提示や、初出時の「全体図＋部分」の対照に使い、ベース画像と同じ一枚にはできない。
    `anchor.asset_id` は**その挿絵自身のアセット id**（いま画像があるもの）でなければならず、ベース画像上の意味エントリでもベース画像でもない。
    不正なレイヤーは書き込み時に拒否される（`pip_invalid`）。使える挿絵アセットが無ければこのレイヤーを書かない。
    挿絵の枠は草稿が画面文字の組の反対側に置く（右側の組→左上、左側の組→右上、中央の組→右上で小さめ）。`text` 層と同じ場所を取り合わない。
  - 画面文字は必ず `text` テンプレート枠（`{ type:'text', role, fields }`）。`role` と `fields` のキーは
    `read_storyboard_context` の `text_spec.roles` から逐語で取り、字数上限は同じ `text_spec.capacity` から読む。
    詳細規則は `layer-text-design` スキルにある。`card` は使わない。`label` は意味位置に固定する文字だけに使い、`anchor` 必須。
  - `anchor` は `must_mark` と同じ意味項目を指し、**本ショットのベース画像となるアセットとそのバージョン**に実在し、型が整合し、
    幾何が揃っている項目でなければならない（`polygon` / `polyline` は折点のある `region` か `line`〈それぞれ 3 点以上・2 点以上〉、
    `marker` は `point`、位置付き `label` は `label`）。位置付き `label` の表示文字は `text` に書き、画面文字はテンプレート枠で出す。
    画面内の特定位置を指さないレイヤーには `anchor` を書かない。
  - **ベースが地図アセット**（`asset_type='map'`）のとき、ベースの要素に固定したレイヤーはショット内で描き直さない：
    レイヤー段はアセットがその要素について既に描いたすべてのレイヤー（線・地点・注記。線種と色はアセットの成図と同じで、
    ショット側では変更できない）をそのまま表示する。`type` は意味種別と整合していればよく、`at_s` が出現時刻を決める。
    同じ要素に別の `label` を追加しない。
  - `at_s`：レイヤー段の何秒目に出すか。**実測音声のタイムラインで組む**：ナレーションが先に言うものを先に出す。
    「同時に」「二手に分かれて」は**同じ `at_s` の二レイヤー**で、「まず…次に…」は異なる `at_s` で表す。
    `at_s` は当該段の `layer_s` を超えてはならない。
- `text_layout`：画面文字の組位置（`text_spec.layouts` の id）。`text` レイヤーがあるなら必ず選ぶ。
  先にベース画像の主題の位置を読み、主題が右なら左側の組、左なら右側の組を選ぶ。同じ zone では後に出る枠が先の枠を置き換える
  （heading 2s → statement 4s は同じ主叙事線）。同じ `at_s` の同 zone 二枠だけが衝突になる。
- `must_mark` の各項目は少なくとも1つの `planned_layers` で描かれるべきで、欠けると `must_mark_not_planned`（警告）になる。
- レイヤー段を持つショット（組み合わせ A / C / D）は `base` 必須。無ければ `missing_base` でブロックされる。

### 2.2.3 `gen_plan`：生成段の計画

- `reference_assets[]`：生成段が必ず使う参照アセット（`{kind, id, name}`、アセット単位）。
  プロンプト作成の工程で一件ずつ照合され、`@アセット名` で参照されない参照アセットは生成をブロックする。
  ナレーションが言及するが本ショットに登場しない組織・遠隔地の人物・遠隔地の出来事には、
  `read_storyboard_context` の `exposition_assets` にある視覚的担体アセットを使う。
  例：「彼はセミョーノフスキー近衛連隊の出身で、その連隊はピョートル1世が自ら創設した」なら、
  画面には近衛連隊の視覚的担体とピョートル1世の肖像が同時に必要であり、空の練兵場に立つ一人ではない。
- **忠実素材と地図は `reference_assets` に入れない**：`faithful` の道具や `asset_type='map'` の地図は決定論的に描かれた証拠画像であり、
  拡散モデルに渡すと描き直され歪められる（サーバは `faithful_in_diffusion` でブロックし、AI 書き込みは拒否する）。画面に出すには
  レイヤー段のベース画像か `type:'image'` のピクチャー・イン・ピクチャー層として使う。生成段が参照するのは演じる必要のある人物・場面・器物だけである。
- `first` / `mid` / `last`：三つのスロットの画面描写（一文でよい。正式なプロンプトは後工程が書く）。
  接続フレームはレイヤー段が継承しロックするので**書かない**：組み合わせ C は `first` を、D は `last` を省く。
- 地理関係を生成段で演じさせない：空き地を歩く人では「イルティシュ川を遡上する」を表現できない。それはレイヤー段の仕事である。

### 2.2.4 段の組み合わせ `combo`

- `combo ∈ A | B | C | D` を記入し、必要なら `suggested_combo` も記入する。既存の選択は保持し、人が確認・変更する。
  `rationale` に理由を一文で書く。
- 四つの組み合わせの判断基準（まず本グループの視覚計画の本ショット項目を見て、それから内容で再確認する）：
  - **A** レイヤー段のみ：図／原資料の上で「どこ・誰・何年」を語る——位置づけ、棚卸し、系譜、収束フレーム。
  - **B** 生成段のみ：「何が起きたか」を語る——本ショットに画面へ落とす追加項目が無く、実測 15 秒以内のときの第一選択。
  - **C** まず位置づけ、それから場面へ：**本ショットに画面へ落とす追加項目があるときだけ**使う。「この出来事はある場所で起きた」は C を選ぶ理由にならない。
  - **D** まず場面、それから図／文書へ着地：結果を図に釘付けする必要があるとき（占領・勝利・死傷・年代）、または次のショットが同じ図で始まるとき、
    本ショットを図で終わらせ、切れ目を「実写 → 図」ではなく「図 → 図」にする。
  - レイヤー段 = 視覚補助と記憶のアンカー（初出で完全に確立し、再言及では短い提示だけ）；生成段 = 想像で補う場面・雰囲気・臨場感。
- A はレイヤー段 ▣ のみ、B は生成段 ▶ のみ、C = レイヤー ▣ → 生成 ▶、D = 生成 ▶ → レイヤー ▣。
  C の生成段の先頭フレームと D の末尾フレームは**接続フレーム ◆** であり、隣接するレイヤーのフレームを継承してロックされる。

### 2.2.5 `budget`：各段の秒数（実測音声が基準）

- `gen_s ≤ 15` は硬性上限（拡散動画モデルの制約）。**レイヤー段 `layer_s` に上限はない**——決定論的レンダリングなので、ナレーションが長い分だけ伸ばせる。
- 提案した組み合わせに従って記入：A は `layer_s` のみ（`gen_s` は null）、B は `gen_s` のみ、C / D は両方。
- **両段の合計は、指示にある実測音声秒数以上でなければならない。** 収まらない場合：
  - AI 書き込みではサーバが不足分を**レイヤー段へ自動で足す**（0.5 秒単位で切り上げ、増やすだけで減らさない。結果はツールの `budget_adjusted`）。
    C / D のレイヤー段は何秒でも合法だが、実測ナレーション +0.5 秒の余裕を残すのが安全；
  - 予算に合わせてナレーションを切り詰める・圧縮する・書き換えることは**絶対に不可**。すでに音声化済みであり、
    文字の変更は音声の無効化を意味する；
  - 本当に収まらないのは **B**（ショット全体が生成段）だけ：実測 15 秒超はブロックなので C または D に切り替え、残りをレイヤー段で担う。

### 2.2.6 `rationale`

600 字以内で、情報点をこう配分した理由、組み合わせとベース画像が本グループ計画のどの項目に対応するか（逸脱する場合は理由と代替）、
本ショットの冒頭画面と前ショットの末尾画面がそれぞれ何か、この切れ目がなぜ成立するかを書く。すでに現れたベース画像で始めるときは、
引き継ぎレイヤーが何を復元し、どの追加項目を加え、何秒目に現れるかを書く。「前ショットと同じ図で空間関係に跳びが無い」は**理由にならない**。
加えて素材不足・注記不足・予算衝突があれば書く。

### 2.2.7 アセット根拠と実現可能性（AI によるカード記入の厳格な制約）

本節が縛るのは **AI の自動生成と AI の書き込みツールだけ**である。人間は情報を補い、注記を作成し、設計を拡張してよく、
この制約を受けない。AI は既存カードの自動書き換え、レイヤー削除、既存制作物の上書きをしてはならない。

1. **現有アセットと既存の制作能力で設計を完結させる。** 設計は現在利用できるアセット画像・属性・意味注記・既存レンダリング能力で
   実現できなければならない。まだ存在しない情報、未作成の注記、推測した地点や経路を、実現条件が整っているかのように書かない。
2. **アセットを選ぶ前に根拠を確認する。** その用途に関係する既存情報を読み、実際に参照するアセットとバージョンを確認する。
   ファイル名・アセット名・別バージョンの画像・他アセットの注記は、参照対象の証拠の代わりにならない。画面内容に関わる判断には
   `read_image` を使い、読んでいないものを見たと述べない。
3. **「未読」と「無いと確認済み」を区別する。** 未読なら読む。無いと確認した後は、それが在るものとして扱わない。
   「後で人間が補う」は設計完了の理由にならない。
4. **すべての依存に実在・整合・実行可能な根拠を。** 画面内の位置・対象・経路・領域に結び付くレイヤーは、ベース画像のアセットと
   そのバージョンに実在し、意味と型が整合し、必要な幾何を備えた意味項目を参照しなければならない
   （`polygon` / `polyline` は折点のある `region` か `line`、`marker` は `point`、位置付き `label` は `label`）。ID や名称は実在一覧からのみ取る。創作せず、
   アセット名を意味項目に見立てず、他アセットや非整合バージョンの同名項目を借りない。**実在しても幾何が空なら根拠にならない。**
   ベース画像と生成段の `reference_assets` は**今すでに画像がある**アセット（原件または生成済み）でなければならず、「後で出図される」前提で
   計画しない。ベースを `version_task_id` で固定する場合、そのアセットの注記がその版に対して作られたと確認できなければ版を固定しない。
5. **アンカーの要否は実際の依存で判断する。** 章タイトル、定義や説明の画面文字（`text` テンプレート枠）、画面内の特定対象や位置を指さないレイアウト要素は、
   そもそもアンカーしない。ただし `label` は型だけでは免除されない（`anchor` 必須）。内容が実際にある場所・領域・経路を
   指すなら規則 4 が適用される。**空アンカー自体は誤りではない。アンカーが必要なのに空であることが誤りである**（幾何レイヤーは丸ごと破棄される）。
6. **注記の無いアセットは、それが実際に支える用途に使える。** 背景、全体提示、欠けている注記に依存しない表現には使える。すべての画像に
   先に注記が必要なわけではない。ただし一般的な河川網を特定の歴史的航路と称したり、「画に川がある」を「その航路の実行可能な経路が既にある」
   と読み替えたりしてはならない。
7. **表現手法は変えてよいが、課題を黙って落とさない。** ある手法が実現できないなら現有アセットが支える別表現に変える。ただし情報点は一つも
   欠かさず、脚本やユーザーが明示的に求めた視覚課題も満たす。ナレーション逐語契約を変えず、画面で示すべき関係を黙ってナレーションだけに
   退行させない。
8. **現状で必要な課題を満たせないなら、完成設計として保存しない。** 代替を検討してもなお満たせないときは `update_storyboard` を呼ばず、
   影響するショットとレイヤー、必要な根拠、現アセットに欠けているもの、既存の代替では満たせない理由を説明する。人間がどの注記を足せば
   実現可能になるかは書いてよいが、それは不足の説明であって設計完了の条件ではない。
9. **ツールの拒否は今のループ内で処理する。** `update_storyboard` が特定レイヤーの参照・型・幾何・実行可能性の誤りを返したら、実際の返答に
   従って修正し、既存のツール呼び出し予算の中で再試行する。参照フィールドを削る、「アンカー無し」と言い換える、人間用の書き込み経路に
   迂回する、独自フィールドを作って成功を主張する——いずれも禁止。

**適格な書き方**

- 地図に `ln-2（キルギス川、line、幾何点 42）` があり本ショットでその川をなぞる：ベースを同じアセットにし、`polyline` を `ln-2` にアンカー。
- 注記の無い河川網図で「江淮水系の全体像」だけが必要：原図を読んだうえで全体提示にし、根拠の無い経路や地点を足さない。
- 純粋な章タイトル「第二章 永徽年間」：`text` テンプレート枠（`heading`、必要なら `date`）を `anchor` 無しで使う。旧来の `card` / アンカー無し `label` は受け付けない。
- 肖像を `image` レイヤーに使う：その肖像アセットにアンカーする（画像が実在することが前提）。

**不適格な書き方**

- アセットに「邗溝の経路」という意味項目が無いのに `anchor.semantic_id = '邗溝走向示意図'` と書く（**アセット名**を意味項目に見立てる）。
- 幾何レイヤー五つすべての `anchor` を空にし、`rationale` に「人手の注記後に補う」と書く（禁じられた「保留付き成功カード」）。
- 別の地図にある同名の `ln-7` を本ショットのベース画像に借用する（アセット跨ぎの借用で座標が合わない）。
- 実在するが点が一つしかない `rg-3` を `polygon` に使う（幾何不足でレンダリング時に丸ごと破棄される）。
- ベースを旧 `version_task_id` に固定したまま、注記は別バージョン向けに作られている（バージョン非整合）。
- 画に川が写っているだけで「史料にある漕運航路である」と述べる（未検証の歴史的結論）。
- 「二手に分かれて進むのが画面で分かること」という明示要求を、難しいからとナレーションだけに落とす。

**保存前チェック**：情報点と視覚課題が揃っているか → 実際のアセットとバージョンを確認したか → 意味の帰属と整合性 → 必要な幾何が実行可能か →
アンカー無しのレイヤーが本当に位置に依存しないか → 「人手の注記待ち」プレースホルダが無いか → ツールが実際に書き込みを受理したか。

### 2.2.8 地図ピクチャー・イン・ピクチャー：全体図と詳細図は独立したアセット（Issue #107）

`read_storyboard_context` の小道具のうち地図アセットには `map_pip` がある：`role: overview`（全体図、`overview_bbox` の経緯度範囲と、各詳細のアセット ID・`label`・`bbox`/`focus_bbox` 取景範囲を含む `details`）または `role: detail`（詳細図、自分の取景と重点範囲、所属する全体図 `parent_asset_id` と全体図の範囲）。**`bbox` が「このナレーションがその詳細に入るか」を判断する唯一の根拠**であり、ナレーションの場所がその取景の外ならベースにしない。`usage` は汎用の用法だけ（特定の集のショット番号で書かれた例は除外済み）。詳細図の `semantics` は全体図の意味を同じ取景で投影したもの（`semantic_id` は全体図と一致）なので、その上で `must_mark` / アンカー付きレイヤーを書ける。意味エントリには `description`（座標根拠＋原文抜粋＋出典）と `keywords`（要素カテゴリ）が付くことがある。**参照を判断する優先順位は、幾何/bbox（選択の根拠）> 画面 > description（補強・否定のみ、単独で選択根拠にしてはならない）> 名称（愛称にすぎない）**。

- 全体の趨勢・範囲・位置関係を語るショットは全体図を `base` に、特定の地理的特徴（河口・合流点・峠・対峙地）に焦点を当てるショットは対応する詳細図を `base` にする。全体図を無理に拡大しない。
- 詳細図は全体図とペアで使う：同じ叙事区間で、隣接するショットに全体図を置き、詳細の場所を示す（確立ショット → 詳細ショット）。
- 同一画面での比較が必要なときだけ合成レイアウト（`map_pip` のレイアウト ID）を使う。通常は 2 ショットの連なりで表現し、複数の詳細を 1 ショットに詰め込まない。
- `stale: true` の詳細は最新の取景案に含まれないため、必要がなければ新規に参照しない。

## 2.3 画面の規律

- 画面描写に**ナレーション本文を書かない**。「ナレーション：…」も書かない。ナレーションは専用フィールドを持ち、二重に書くと二度読まれる。
- ドキュメンタリーに**セリフは無い**：`役名：「セリフ」` は禁止。画面の人物に解説を喋らせてはならない。
- 画面には観客が実際に見るものを書く：主体、動作、ショット内の変化（広げられる地図、行進する隊列、めくられる文書）。

## 2.4 尺とビート

- 本ショットの尺 = `budget.layer_s` + `budget.gen_s`（存在しない段は 0）。かつ実測音声時間以上であること。
- 上限は生成段のみ硬性（15 秒以内）。**レイヤー段に上限はない**（決定論的レンダリング、Issue #110）。
- 脚本中の `【ビート名】` 表記はハードカットの境界であり、1ショットがビートをまたいではならない（第1段階の分割時点で守る）。
- 尺合わせのために二つの主情報点を1ショットへ詰め込まない。一文を二ショットに分けて読ませない。
