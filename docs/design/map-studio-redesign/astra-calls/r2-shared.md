## 3. 主 agent 裁定（权威，覆盖评审中「待用户决策」项；必须原样落地，不得改写为待定）

### R-A（V5 / M1）：确认与渲染的保证范围

- 用户工作流明确要求「人核对确认后才渲染」。**默认 guided 流程在 base 就绪后停靠；未经人显式「确认几何并
  渲染」不得进入 drawing。** 这是 **UI + guided 契约层**的保证（默认流程），不是服务端闸门。
- 服务端事实：当前没有任何「未确认几何禁止 drawing」的闸门（facts §6.9）；`auto` 会连续推进到 complete 并
  交付。文档必须如实分列「原要求 / 已核实事实 / 实际保证 / 不保证范围」四栏，不把保证写成服务端强制。
- **不新增不可恢复的 `reviewedInputKey` 正式门槛**（删除该设计）：确认动作 = 复用既有要素确认状态（`PUT
  map_spec` 去掉 `proposed`）+ 独立的显式「渲染成图」按钮。刷新后按服务端事实重算「未确认要素数」，不依赖
  浏览器内存里的整体复核标记。
- `auto` 只在 AI 活动抽屉内作为明确启动命令，启动前警告：可能越过人工核对并连续执行到交付。
- 第 05 文档：V5 标为「设计闭合（主 agent 裁定）」，G5 标为「已裁定：保证范围 = 默认 UI/guided；服务端仍不强制」。

### R-B（M2）：地点行与点列表弹窗的保存

- 地点行与「全部地点」/顶点弹窗内的编辑**只改页面几何草稿**（`specDraft`）；关闭弹窗不二次提交。
- **页面「保存几何」是唯一写服务端的动作**，一次页面级 CAS：提交整份页面几何草稿（若几何未变，发服务端
  原样 spec）+ `layer_options`；成功基线 = 服务端返回的规范化 spec 与 revision。
- 弹窗内状态文案：「已加入待保存草稿 / Added to unsaved draft」；页面保存成功后才显示「已保存」。
- 多脏条目：**不存在「只提交部分行」的提交粒度**——页面只有一个几何草稿，保存即提交当前整份草稿；条目
  「完成编辑」只结束局部事务，不承担保存仲裁。
- 结果未知（断线/超时）：不得断言未落盘、不得盲重发；先读 detail：revision 前进且内容匹配 → 视为已保存；
  不匹配 → 冲突副本（保留既有 5d 口径，但写清判定步骤）。

### R-C（M6）：阶段驱动的空间分配

## 4. 事实校正清单（facts §6 已核实；文档里凡与这些冲突的句子必须改写）

1. **底图成品缓存已经存在**：`geo/base-render.ts:483-643` 已有签名缓存（目录 `map-bases/<sig>.png` +
   sidecar）。设计不再是「新建缓存系统」，而是「修正既有缓存的键与安全性」：键缺 NE 数据集 sha、DEM manifest

   无单飞。
2. **complete 阶段就是交付**：`run.ts:264-275` → pip 细节渲染 → `buildDeliverable` → `deliverCurrent` →
   `finish(proceed:false)`，最终 `status='completed'`。没有「只准备不交付」的调用。
3. **`/deliver` 是重试/补交付**：`delivery.ts:69-86` + `routes.ts:141-148`，要求 stage=complete、非 running，
