# 实验：设计卡「窗口化上下文」+ GLM 5.3 flash 智能路由（2026-11-13）

> 实验性质：只做对照，不合并、不发布、不写生产。全部运行在隔离 worktree + 复制数据库 + 独立端口。

## 1. 背景与问题

生产实测（ep27 / drama 20，113 镜，任务 3069，`GET /api/v1/tasks/3069/observations`）：
每镜 5–10 次模型调用、约 7.5 分钟；调用提示词从第一轮 ~32.7k 涨到之后每轮 ~160k——
因为 `read_storyboard_context` 一次把**整集**（全剧本 + 113 张设计卡 + 全部资产）塞进上下文。

两个要回答的问题：

1. **速度**：把上下文缩到「本镜 ± 3 镜」能不能显著变快？（A vs C）
2. **质量**：GLM 5.3 flash + 窗口化上下文（看图仍走 DeepSeek）能不能与 DeepSeek 相当？（C vs B）

## 2. 实验设置

- 代码基线：`origin/master` = `5c232f36`（issue/99 phase 1 合并后的 master），throwaway 分支 `exp/design-card-window`（不合并、不推送）。
- worktree：`../huobao-drama-exp-designcard`；`backend/node_modules`、`frontend/node_modules` 软链到主仓库。
- 数据库：SQLite backup API 复制生产 `data/huobao.sqlite3`（14:21Z 快照），复制后把 `sys_task` 里 processing/pending 的行标 failed、
  运行中的 keyframe/video batch 标 cancelled（避免复制库去拉生产的产物）。
- 数据目录：`HUOBAO_DATA_DIR=<worktree>/data`，`data/static` 软链到生产 `data/static`（只读使用）；数据库用 `SQLITE_PATH` 指向复制库。
  独立的 `DATA_ROOT` 是必须的：`layer-fonts.ts` 会在 `DATA_ROOT/fontconfig` 写 fontconfig 配置，指向生产数据目录会覆盖生产字体配置。
- 后端：`PORT=5699`（**不是** 5689——5689 已被另一个 Issue #99 的隔离 QA 实例占用，`/tmp/i99-qa`），`NODE_ENV=development`，
  `AI_MAX_TOKENS=131072`（来自复制的 `backend/.env`）。
- 复制库里只改两条文本配置：config 1「GLM 5.3 (local)」`is_active=1`、`model=["glm-5.3-flash"]`；config 10「DeepSeek V4.1 Flash 1017 (local)」保持 `is_active=1`。
  两条配置的 `suspended_at` 都清掉（复制库里 config 10 是 14:05Z 生产自动暂停的现场，config 1 是 11-10 的旧暂停）。
- 看图路由不变：`read_image` 走独立环节 `read_image（vision:true）`，只有 `vision=1` 的配置能被选中 → GLM（vision=0）不可能被选，
  实测 18 次 vision 调用全部落在 config 10（见 §6）。

### 2.1 代码改动（仅 worktree，实验开关）

1. `agents/tools/storyboard-tools.ts`：`read_storyboard_context` 在 `storyboardPromptScope='design_card'` 且窗口 N>0 时返回窗口内容：
   - `existing_storyboards` 只含本镜 ± N 镜（默认 N=3），每镜只含 `id / shot_number / title / narration / duration / combo / design_card`；
   - 不再返回整集 `script`（本镜旁白由逐镜 `narration` 给出）；
   - `characters / scenes / props` 只保留这些镜头**引用**的资产，或名字/语义条目名与窗口旁白有 ≥3 字连续重合的资产（窗内语义相关）；
     道具的 `semantics` 因此也只剩这些道具的；
   - `text_spec`、`aspect_ratio`、`composition`、技能、系统提示词、工具集、校验器全部不变；
   - 缺省 N=0 → 与改动前逐字一致（A 臂即走这条路径）。
2. `agents/context.ts`：`designCardContextWindow` 请求上下文值 + `getDesignCardContextWindow()`（env `DESIGN_CARD_CONTEXT_WINDOW` 只是缺省值）。
3. `services/design-card-batch.ts` + `routes/design-cards.ts`：fill 请求新增可选 `context_window`（0–12 的整数），写进任务 params，便于事后解释提示词体积。
4. `services/text-scheduler.ts`：env `DESIGN_CARD_ALLOW_TEXT_MAIN=1` 时放宽 `design_card` 环节的「必须是视觉模型」限制——
   因为看图本来就由独立的 `read_image` 环节负责。**这是 B 臂能跑起来的前提**：`AI_STAGES.design_card` 现在是 `vision: true`，
   钉住 GLM（vision=0）会被 400 拒绝。其他环节（含 `read_image`）的视觉要求不变。

- 窗口版**不是**把资产砍到只剩"被引用"的：名字/语义条目名与窗口旁白有 ≥3 字重合的资产也会留下，
  否则「乌拉尔山东西两麓领地范围图」这种长名会被旁白里只说「乌拉尔山」的镜头漏掉（实测 #4 保留了 11 个道具，
  包括 257 乌拉尔山图 / 266 叶尔马克肖像 / 276 苏里科夫画）。#18/#19 只留下 4 个道具仍能完成任务（见评审结论）。
- 折算成提示词：系统提示 + 技能 + 工具定义约 32.7k tokens（DeepSeek）/ 37.1k（GLM 分词），
  所以整集上下文在**卡片写满之后**是 32.7k → 160k 级别（生产任务 3069 实测 161,402 峰值），
  窗口版是 32.7k → 47–52k。这正是生产每镜 7.5 分钟的根源。

## 5. A 臂的数据来源与偏差说明（重要）

A 臂**没有**在复制库上新跑一遍，原因与做法：

- 14:05Z 生产 config 10 因 4 次连续超时被自动暂停（主控 14:44Z 恢复）。生产 ep27 的整集设计卡批次任务 3131
  （53 镜、`context_window=None`、config 10）从 15:04Z 一直跑到 16:40Z 仍只有 14/53；
  在它运行时再叠加 6 次 ~160k 上下文的 DeepSeek 请求，就是把当天导致暂停的负载再加一份。
- 所以 A 臂取**生产自己的整集上下文输出**：任务 2942（06:32–07:20Z，config 10，`deepseek-chat`，整集上下文）。
  6 个目标镜的卡不是从备份库取，而是从 2942 的观测消息里取模型**自己**的 `updateStoryboard` 工具调用参数
  （`task_observed_call` + `task_observed_message.text_hash → task_observed_text`）——人工通过 PUT 改过的卡不会出现在那里。
  6/6 全部取到了模型原始输出（每镜 5–8 次调用、work_ms 78–562s）。
- 偏差（必须一起读）：
  1. 2942 运行时本集只有约 30 张设计卡，整集上下文是 ~70–90k tokens/次调用；**卡片写满之后**是 161k
     （生产任务 3069 实测）。所以 A 的 `ptok`/`wall` 偏小，是"低密度整集上下文"，不是最坏情况。
  2. 2942 与其它文本任务并行、生产机器有竞争；它的 `llm_ms` 中位 17–101s 因此包含排队/竞争，不能当作纯计算时间。
  3. 因此 A vs C 的**墙钟**不可直接相减（A 在 07:00 跑，C 在 16:00 跑，DeepSeek 负载差一个量级）。
     可靠的结论只有两条：**提示词体积**（A 74.9k vs C 46.2k tokens/主模型调用；卡片写满后是 161k vs 46k）
     和**每镜调用次数**（A 6.0 vs C 5.5，窗口没有削减工具往返次数，削减的是每次往返的上下文）。
  4. 14:12Z 生产备份里的同 6 镜卡片比模型原始输出**短**（例如 #4：1,990 vs 3,066 字符），说明生产阶段人工改过/精简过卡；
     这些备份版本没有被用作 A 臂。

## 6. 看图到底在问什么（智能路由的依据）

四个臂在 6 个目标镜上共 26 次 `read_image` 调用，全部落在 **config 10（DeepSeek）**——GLM（vision=0）一次都没被选中，
说明"文本模型走 GLM、看图自动走 DeepSeek"这条路由在现有代码里已经天然成立（`read_image` 是独立环节）。

调用问题的内容（逐条见 `exp/vision_calls.json`，摘要如下）：

| 臂 | read_image 次数 | 超时（120s 上限） | 问的是什么 |
|---|---|---|---|
| A（整集 + DeepSeek） | 9 | 0 | 地图上可读标签/色块位置、哪片区域留白可压文字 |
| B（GLM 窗口） | 7 | 3 | 同上 + "这张场景定妆图里营寨/木栅在哪个像素区域" |
| B2（GLM 窗口 low） | 1 | 0 | "哪些区域留白适合放屏幕文字而不挡地名" |
| C（DeepSeek 窗口） | 9 | 0 | 同上 |

26 次调用里，25 次问的是**构图/留白/文字框可用区域**，1 次问"这张道具图上有没有文字"。
**没有任何一次**问历史事实、语义判断或"这幅画表达的年代对不对"。也就是说，看图在这个环节里
只承担「底板留白与主体位置」的排版信息，是**排版依据**，不是**内容依据**：

- 内容判断（这一镜要让观众 get 什么、用哪张资产、图层画什么）完全可以由纯文本模型做主，
  因为资产清单、`semantics` 名称、`text_spec` 容量都在文本上下文里。
- 排版细节（主体在左/右、哪块留白能压 3 行字）必须看图；这部分短小（提示词 250–1,000 tokens、回答 200–700 tokens），
  可以永远交给一条便宜的视觉配置，与主模型解耦。
- B2 说明这条路可行：整镜只调了 1 次 `read_image` 就完成排版决策（#8），其余 5 镜 0 次——GLM 直接用
  `semantics` 里的条目名称（例如 "r_dc64e2ed 乌拉尔山脉中段走向线"）推断位置，图谱类镜头仍然落库成功、0 阻断问题。

超时说明：B 臂有 3 次 `read_image` 触到 120 秒上限（C/B2/A 在目标镜上各 0 次），全部发生在生产批次 3131（160k 上下文）同时运行的时候。
按主控要求，这些超时记为**数据**（引擎竞争），不记为质量失败——三个臂的卡都落库成功。

## 8. 结论

### 8.1 窗口化到底省了什么（A vs C）

- **上下文体积**：整集 290,468 字符 → ±3 窗口 30.6k–34.0k 字符，**8.6–9.5 倍**（同一份 113 镜、卡片写满的库）。
  折算成真实提示词：每镜第一次调用 32.7k（DeepSeek）/ 37.1k（GLM）tokens，之后整集上下文是 73–90k（A 臂、卡片只写了 30 张时）
  或 **161k（生产 3069，卡片写满时）**，窗口版是 **46–52k**。主模型调用的提示词中位：A 74.9k vs C 46.2k（低密度下 1.6 倍；
  按生产写满密度算约 3.5 倍）。
- **调用次数没有变少**：A 6.0 次/镜、C 5.5 次/镜（工具往返结构不变），窗口省的是每一次往返的体积，不是往返次数。
- **墙钟不能直接相减**：A 中位 100.7s、C 中位 295.2s，但 A 跑在 07:00（DeepSeek 空闲）、C 跑在 16:00（生产 160k 批次同时在跑）。
  同一时段的对照里，`llm_ms` 中位 A 17–101s、C 22–55s，差异被排队时间吞掉。
  参考生产的真实速率：任务 3069 在 160k 上下文下约 7.5 分钟/镜；本实验窗口版实测中位 4.9 分钟/镜（同等工具往返），
  方向一致但幅度受引擎竞争影响。**结论：窗口化是确定的 3–9 倍输入体积削减，墙钟收益取决于引擎是否被输入 token 卡住；
  单靠窗口化不可能把 7.5 分钟变成 1 分钟——换模型（B2）才是量级差异（见 8.2）。**
- 反向证据：A 臂有几处「整集上下文」反而更快（#4 107.8s vs C 177.5s），说明在小镜头上，上下文体积不是瓶颈。

### 8.2 模型效应（C vs B / B2）

| | C（DeepSeek 窗口） | B（GLM flash 窗口，默认思考） | B2（GLM flash 窗口，`reasoning_effort=low`） |
|---|---|---|---|
| 墙钟中位/均值 | 295.2s / 268.5s | 360.2s / 464.5s | **55.0s / 60.1s** |
| 完成 token/镜（≈思考） | 3.1k | 13.2k（最高 51k） | **2.1k** |
| Fabel 均值 | 5.73 | **8.17** | 7.83 |
| 卡保存 | 6/6 | 6/6 | 6/6 |
| 阻断问题 | 0 | 0 | 0 |

- **GLM flash 的默认思考是灾难**：单次调用思考 13–51k tokens，#11 一镜 20 分钟。加 `reasoning_effort=low` 后同一镜 42 秒，
  思考降到 1.5–4.1k tokens，**6 倍以上加速**。
- **质量上 GLM（低思考）不输，甚至更好**：盲评均值 B 8.17 / B2 7.83 vs C 5.73 / A 6.2。评委给的失败理由集中在两类硬伤：
  把证据素材当可重绘素材、`inherit_prev` 前提不存在、把下一镜的内容提前剧透、文本框压到图上已有的标注区。
  GLM 卡在这四项上明显更少，DeepSeek 两臂的卡更多犯「承诺了不存在的底图/语义」这类错误。
- **判读注意**：A 的卡由生产环境的老版本代码写出（rationale 无 600 字上限），B/B2/C 的卡由本 worktree（master 5c232f36）
  写出，`serializeDesignCard` 把 rationale 截到 600 字（`backend/src/services/design-card.ts:54 MAX_RATIONALE`），
  评委在多张卡上抱怨「rationale 截断」——这是**代码版本差异**，对 B/B2/C 略不利，仍不影响结论方向。
- 结论：**B2 是可接受的**（质量不低于 DeepSeek、速度快 5 倍、阻断问题 0）；**B（默认思考）不可接受**（慢且贵，无质量优势）。

### 8.3 哪些调用真的需要看图（智能路由怎么切）

26 次 `read_image` 全部落在 config 10（GLM 一次都没被选中），25 次问的是「主体在画面哪个位置 / 哪块留白能压文字 /
图上可读标注在哪」，1 次问「这张道具图上有没有文字」。**没有一次问历史事实或语义判断。**

所以路由应该这样切：

- **主模型（做内容决策）→ 纯文本模型即可**（GLM 5.3 flash + `reasoning_effort=low`）：资产清单、`semantics` 名称、
  `text_spec` 容量全在文本上下文里，窗口 ±3 就够。
- **`read_image` → 专门的视觉配置（DeepSeek 现在这条）**：只需要排版信息，问题短、回答短（250–1,000 tokens），
  与主模型解耦；GLM 臂 6 镜里 5 镜一次都没调用它也能落卡（直接按语义条目名推断位置），说明调用它是"排版保险"而不是必需。
- 唯一需要视觉配置**存在**的前提是 `AI_STAGES.design_card` 当前被标成 `vision: true`（`backend/src/services/ai-stages.ts`），
  它会拒绝非视觉主模型。实验里用 env `DESIGN_CARD_ALLOW_TEXT_MAIN=1` 放开（B/B2 臂就是这么跑起来的）；
  若要上线，正确的改法是：设计卡环节改为 `vision: false`（看图由 `read_image` 环节负责），并在 UI 上把「主模型」与
  「读图模型」分成两个可选项。
- 副作用值得记：今天 14:05Z 生产 config 10 因连续超时被暂停，正是因为主模型和看图共用同一条 DeepSeek。
  拆成「GLM 主 + DeepSeek 只看图」后，DeepSeek 的负载从「每镜 5–7 次 160k 调用」降到「每镜 0–2 次 250–1,000 token 调用」，
  这条自动暂停的风险也随之消失。

## 9. 局限

- 6 个镜头、单个评委、单次评审；每镜仅 1 个样本，评分差异 0.3–1 分以内的不要过度解读。
- A 臂是生产旧版本代码的输出（rationale 无 600 字上限、上下文 73–90k 而非 161k），且与其它文本任务共跑，墙钟不可比。
- 三臂都在同一复制库、同一批 TTS 实测时长、同一套工具/技能/校验器上跑，只有主模型和上下文窗口不同；
  但 B/B2 用 env 放开了「设计卡必须视觉模型」的限制，这是实验开关，不是产品行为。
- 今天 DeepSeek 有引擎竞争（生产 160k 批次同时运行），B 臂 3 次 `read_image` 触到 120s 上限；这些记为数据不记为质量失败。
